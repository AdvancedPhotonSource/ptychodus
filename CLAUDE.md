# CLAUDE.md

## Project

Ptychodus is a ptychography data-analysis application that ingests instrument data, prepares it for processing, and dispatches it through pluggable reconstruction libraries (PtyChi, PtychoPINN, and others). It runs as a PyQt5 GUI, a headless batch CLI, and a streaming processor inside beamline pipelines (pvapy area-detector). Python ≥3.11, `uv` preferred.

## Common Commands

```sh
uv sync --extra globus --extra gui --extra ptychi   # dev install; ptychi is CPU torch
uv sync --extra globus --extra gui --extra ptychi-cuda130  # GPU: match nvidia-smi's CUDA ceiling
uv run ptychodus                                    # GUI
uv run ptychodus -b reconstruct -i <in> -o <out>    # batch — reads StandardFileLayout in <in>/
uv run pytest                                       # tests
uv run ruff check . && uv run ruff format --check . # lint + format
uv run mypy src/ptychodus scripts tests             # types (wider than CI's)
```

Container builds: `scripts/podman/build` (Dockerfiles in [containers/](containers/); tags `ptychodus:<version>-<variant>` over the script's `DEFAULT_VARIANTS` — CPU, each supported CUDA, ROCm, XPU). Release images install the PyPI release named by `PTYCHODUS_VERSION` (default: latest) over their base image's accelerator torch; `Dockerfile.dev` (variant `dev`, on request) installs the checkout and backs the devcontainer. Backends on no index (PtychoPINN and others) get wheels built from sibling checkouts. The launcher `scripts/podman/ptychodus` picks the GPU family and, on NVIDIA, the newest built CUDA variant the driver supports. Docs: `make -C docs html`.

Other entry points (`ptychodus-reconstruct`, `ptychodus-webapp` and the rest) are in [pyproject.toml](pyproject.toml) `[project.scripts]`, with modules in [src/ptychodus/cli/](src/ptychodus/cli/). Unpackaged operator tooling — the podman wrapper, the per-facility HPC token/submit helpers — lives in the top-level [scripts/](scripts/) and runs from a checkout, e.g. `python scripts/genesis/ptychodus_iri_tokens.py`.

### Testing

Tests cover `api/`, `model/`, `view/widgets/` and the Qt-free `controller/rendering/` (tested at `tests/` root, on a bare install), plus the two `controller/` modules with real logic: [controller/parameters.py](src/ptychodus/controller/parameters.py) (unit conversion, signedness inference, complex amplitude/phase editing) and [controller/processing/generated.py](src/ptychodus/controller/processing/generated.py), the mostly pure `Sequence[DescribedField] -> list[_Item]` pipeline laying out each backend's panel. A reusable widget with logic of its own belongs in `view/widgets/`, like `DecimalRangeSlider`. **Do not add tests for anything else under `view/` or `controller/`**, controller helper functions included. [tests/conftest.py](tests/conftest.py) drops `tests/view/`, `tests/controller/` and `tests/webapp/` via `collect_ignore` when their extra is missing, and hosts the session-scoped `qapp` fixture, which imports `QApplication` inside so the conftest imports on a bare install. `pytest tests/` must pass on a bare `pip install .` (what CI runs), so nothing reachable from `ptychodus.model` at import time may need an optional dependency — an optional subsystem defers its import, as a reconstructor backend does inside `_build()`. Guard a test that needs an optional backend with `pytest.importorskip('ptychi')`; drop an optional-extra directory with `collect_ignore` in the conftest — `importorskip` there is reported as an error, not a skip.

## Architecture

### Three-layer separation: api / model / view+controller

- **`src/ptychodus/api/`** — pure-Python, stateless domain layer: core data structures (`Product`, `ProbeEnsemble`, `Object`, `ProbePositionSequence`, `DiffractionDataset`, `AssembledDiffractionData`), abstract interfaces (`DiffractionFileReader/Writer`, `ProductFileReader/Writer`, `Reconstructor`, `TrainableReconstructor`, `WorkflowAPI`), and `PluginRegistry` with its read-only `PluginCatalog`s. Module names follow SciPy: activity verbs for operations (`interpolate`, `reconstruct`, `propagate`, `simulate/` for forward models, `preprocess/` for preprocessing pipelines), plural collections for infrastructure (`plugins`, `constants`, `typing`), singular nouns for domain types (`affine` owns `AffineTransform`, its decomposition, its estimator and the product-level correction). It depends on nothing else in ptychodus and holds no application state — observers, parameters, settings and plugin selection live in `model/`. [tests/test_layering.py](tests/test_layering.py) fails on any import from `api/`, `plugins/` or `webapp/` into `model`, `view` or `controller`.
- **`src/ptychodus/model/`** — application logic, used by the GUI *and* by `__main__.py` batch mode. Most subpackages (`diffraction/`, `product/`, `processing/`, `fluorescence/`, `analysis/`, `globus/`, `genesis/`, and others) expose a `*Core` class owning their settings, repositories and APIs; reconstructor backends expose a `*ReconstructorLibrary` instead and live under `plugins/`, discovered rather than composed. `model/core.py::ModelCore` is the composition root, constructing them all in dependency order.
- **`src/ptychodus/view/`** (PyQt5 widgets, no logic) and **`src/ptychodus/controller/`** (mediates widgets↔model) mirror the model layout, with composition roots `view/core.py::ViewCore` and `controller/core.py::ControllerCore`; the navigation toolbar order in `ViewCore` is the source of truth for left/right stacked-panel indexes. `controller/rendering/` is not mediation but Qt-free array-to-color transformation (`VisualizationEngine` and its renderers); only the GUI drives it, so `ControllerCore` builds every engine and no `*Core` holds one. Two `__init__.py` files are deliberately empty and say why — `controller/` keeps `controller/rendering/` importable without PyQt5, `controller/diffraction/` breaks an import cycle with `controller/product/` — so import both composition roots from their `core` modules.

The GUI is optional: `__main__.py` falls back to headless if PyQt5 is missing. `ptychodus_stream_processor.py` (the `PtychodusAdImageProcessor`) is a third entry mode, imported only when `pvapy` is available.

### Index-based pattern/position association

Diffraction patterns and probe positions are paired by **integer scan index**, never by array order. This is what makes streaming and mismatched-rate ingest robust.

- Producers: `DiffractionArray.get_indexes()` (`api/diffraction.py`); `ProbePosition.index` (`api/probe_positions.py`).
- Matcher: `interpolate_at_indexes` in `api/interpolate.py` is the rule's home; `prepare_reconstruct_input(assembled_data, product, ...)` in `api/reconstruct.py` and the STXM-DPC object generator both pair through it. Pattern indexes are authoritative — duplicate position indexes are averaged into anchors, pattern indexes inside the anchor range without an exact position are linearly interpolated, and those outside it are dropped (no extrapolation).
- Round-trip: HDF5 and NPZ product writers persist position indexes via `ProductFileKeys.PROBE_POSITION_INDEXES`.
- Line-major indexes: when a positioner records more points per scan line than the detector, a running count on either side slides the pairing by the surplus, line by line, yet every pattern still finds a match. A registration passing `line_index_stride` to `MDAPositionFileReader` or `APS2IDDiffractionFileReader` instead numbers a point `line * RASTER_LINE_INDEX_STRIDE + column` (`plugins/mda/mda_position_file.py`), so the unchanged matcher leaves surplus commanded points unclaimed, lets a short line claim fewer, and drops a detector line past the end of the positioner record. The default numbering is untouched.

### Plugin system

`api/plugins.py::PluginRegistry.load_plugins()` walks `ptychodus.plugins.*` with `pkgutil.iter_modules` and calls each module's `register_plugins(registry)`. Module-load failures are logged and skipped — this is how optional-dependency plugins (LCLS, NSLS-II, …) silently disable themselves. Never make plugin loading fatal.

**Registration in `api`, selection in `model`.** Plugin modules register into each registry field's `PluginList`; `load_plugins` freezes them into read-only `PluginCatalog`s — sorted by display name, looked up by either name — and a late `register_plugin` warns and is skipped. The current selection lives in `model/plugins.py::PluginChooser`, an `Observable` over one catalog. `ModelCore` wraps each catalog a core selects from **once** and hands that chooser to every consumer: a settings-backed `PluginChooserParameter` and a dialog's `FileTypeChooser` share it, and a second wrap would hold an independent selection. Lookup-only categories — generators, probe presets, training-data writers — are passed as catalogs. A chooser does not see later registrations, so finish a self-made `PluginList` before wrapping it.

**A file handler names itself.** Every reader and writer interface is a one-line subclass of `api/files.py::FileReader[T]` or `FileWriter[T]`, whose `FileHandler` base builds the Qt name filter `get_file_filter()` from the abstract `get_file_description()` and `get_file_extensions()` — extensions carry a leading dot to compare against `Path.suffix`, and are sorted so the filter is stable. `register_plugin` derives `display_name` from that filter, so a file-handler registration passes only `simple_name`; `display_name` is for plugins that are not file handlers (generators, presets, fluorescence enhancers, workflows, reconstructor libraries). Either mistake warns and is skipped rather than raising, because `load_plugins` catches only `AttributeError`. A class serving several instruments takes its description as a constructor argument rather than being registered twice under one instance.

### Settings & observers

Settings flow through `model/parameters.py::Parameter[T]` and `ParameterGroup`: each `*Core` calls `settings_registry.create_group(name)` and creates typed parameters, and `model/settings.py::SettingsRegistry` serializes the tree as INI. React to changes by hooking `Observer`/`Observable` (`model/observer.py`) rather than polling. `model/plugins.py::PluginChooserParameter` adapts a `PluginChooser` into a settings-backed `Parameter[str]`, the typical bridge from settings string to selected plugin; the reconstructor selection is two in series — a library from the chooser, then an algorithm resolved against that library.

**Three idioms, and which to reach for.** A hand-written `*Settings` class backs every subsystem and is what a new `*Core` writes. The other two start from a pydantic object — `Reconstructor.get_default_options()`, `ProbePositionsGenerator.get_default_options()` — and differ in who wrote it.

A declaration **ptychodus owns** is read straight by `model/declared.py`: `describe()` takes bounds, choices and display text off each `Field` and spells its key from the field name (PascalCase, unit suffixes in words, an optional `prefix` for one of several like branches); `declare_in()` creates the live parameters and `restore()` writes them back. No policy, overlay or table. A new declaration uses this, as the scan-pattern, probe- and object-generator plugins, the fluorescence enhancers, cdtools and PtychoPINN do.

A declaration **ptychodus does not own** cannot be annotated at the source, so `model/processing/flatten.py` projects it and a per-backend table supplies what upstream omits — display text, bounds, choices, renamed keys, adapters bridging one field onto several. pty-chi is why it exists. **Transitional**: it retires with the Qt panels.

Both reach the GUI and the reconstruct path through `ProcessingParameterStore` — `register_declared` for the first, `register` for the second. The fluorescence enhancers' branch table lives in `model/fluorescence/core.py`; each enhancer persists in its own group and lays out with the same generated panels. All three idioms owe this: a parameter states its bounds where it is declared, because `controller/parameters.py` raises on a missing one rather than degrading, and infers signedness from the minimum.

### Standard HDF5 layout (external interface — change carefully)

`api/io.py::StandardFileLayout` is the contract for batch mode, remote workflows and the `ptychodus-reconstruct-*` drivers: `diffraction.h5`, `product.h5`, `fluorescence.h5`, `ptychi_options.yaml`, `settings.ini`, `ptychodus.log`, and a `model` stem whose extension the trainable backend supplies. Input versus output is the containing directory (batch mode's `-i`/`-o`; remote workflows stage under `<workflow_root>/input/` and `<workflow_root>/output/`). The enum's `path(directory)` and `checkpoint_path(directory, epoch)` helpers build paths, the latter `<stem>.<epoch:06d><suffix>`, the per-epoch snapshot convention for streaming reconstructions. Key names, which external consumers depend on, live in `DiffractionFileKeys` / `ProductFileKeys`; CXI paths in `CXIFileKeys`, with `CXIVariant` choosing a writer's layout — readers detect it and take no variant.

### Reconstructor libraries

Each backend exposes a `*ReconstructorLibrary`; the base in [api/reconstruct.py](src/ptychodus/api/reconstruct.py) owns everything but what the backend builds. A subclass passes `requires=` — the modules it cannot work without — and implements `_build()`. The base resolves those names without importing them (`is_available()`), calls `_build()` once on first `__iter__`, and logs through the library's own logger: the version on success, `<distribution> not found.` at INFO when the modules are absent, and a **warning** with traceback when they resolve but `_build()` raises `ImportError` — a fault, not an uninstalled backend. So a backend writes no availability logic, no entry-point string (the base points each reconstructor at the library's own `_subprocess.py`), and never imports its dependency at module scope. A library is named where it registers; the section table and parameter store key on that name. The surface is stable whether or not the backend is installed, so `ModelCore` hands `ProcessingCore` the whole chooser and `ProcessingCore` answers which backends are in play. Reconstructors yield `ReconstructOutput` per iteration so the GUI can stream progress.

**A backend reconciles conventions at its own boundary.** ptychodus stores a probe in photons per pixel — `sum|P|^2` is the photons incident per exposure, so an energy-conserving propagator gives a detector total of `sum|P*O|^2` — and probe positions in meters. A backend whose forward model or coordinate frame differs converts on the way in and applies the inverse to every yielded `ReconstructOutput`, so a stored product is in ptychodus's convention whatever produced it, and one backend's output is another's warm start. Measure the scale against the backend's own forward model rather than hardcoding it — pty-chi's normalization differs between far and near field.

### Remote compute

Both providers are optional-dep gated but constructed by `ModelCore` even when disabled:

- `model/globus/` — Globus Compute (original APS workflow).
- `model/genesis/` — IRI/AmSC HPC via `facility_adapters.py`, with per-facility scripts under `scripts/genesis/{alcf,nersc,olcf}/`.

`WorkflowAPI` (`api/workflow.py`, `model/workflow.py::ConcreteWorkflowAPI`) is the unified façade GUI, batch, and remote drive.

### ptychodus.webapp service

`src/ptychodus/webapp/` is the read-only web service, run as `ptychodus-webapp` from the `webapp` extra. It reads only from `ptychodus.api` and **must not import `ptychodus.model`, `ptychodus.view` or `ptychodus.controller`** — enforced by [tests/test_layering.py](tests/test_layering.py) — and nothing outside it imports it, so a bare install never touches its dependencies. Surface: FastAPI REST under `/api/v1/*`, MCP server at `/mcp`, minimal TypeScript UI at `/ui/`, SQLite metadata cache reconciled by a watchdog observer. Composition root: `create_app()` in `app.py`. Deployment: [src/ptychodus/webapp/README.md](src/ptychodus/webapp/README.md).

## Conventions

- Ruff: **single-quoted** strings, 100-char lines, py311 target. Enabled rules: F, N, NPY.
- Preserve unit suffixes on physical quantities (`probe_energy_eV`, `set_value_from_string`) — silence naming lints with `# noqa: N802/N806/N815`, don't rename.
- Type hints are mandatory. `pyproject.toml` lists modules whose missing stubs are intentionally ignored — keep new code typed and don't widen that list.
- `ModelCore.is_developer_mode_enabled` is `True` when the effective log level ≤ DEBUG (`--log-level 10`); some controllers gate features (Agent panel, probe-position analysis) behind it.
- HTTP-client code uses `httpx` throughout (sync `httpx.Client` for repeated calls, module-level `httpx.get/post` for one-shots). `requests` is not a dependency.
- **No hand-rolled pickling.** An object crosses a process boundary as itself, never as `pickle.dumps` bytes, on the `SimpleQueue` [api/spawn.py](src/ptychodus/api/spawn.py) hands the child. `SimpleQueue.put` pickles synchronously, so a later in-place edit cannot tear the array and an unpicklable message fails at its own `put` as `ChildError`, not silently on `multiprocessing.Queue`'s feeder thread. The one explicit pickle is `send_error`'s, so an unrebuildable exception costs only `child_exception`. Persisted data never pickles (`numpy.load`/`savez` keep `allow_pickle=False`, `torch.load` takes `weights_only=True`); a test may, to pin transport survival.
- Prefer affirmative conditionals when both branches do meaningful work — `if x.is_file(): ... else: ...`, not the negated form. Guard clauses that early-return are still idiomatic.
- **No forward references in comments.** A comment or docstring explains what the code guarantees, not who consumes it. Naming a caller is wrong the moment one is added, moved or renamed. In `api/` it is worse than stale: naming a `model/` or `cli/` symbol inverts the layering the package exists to enforce, even in prose. Describing what the code itself depends on is fine — an import already states it.
- **Array annotations name a dtype.** Bare `numpy.ndarray` and `numpy.dtype` mean `Any` while looking annotated. Use a dtype-family alias from [api/typing.py](src/ptychodus/api/typing.py) (`RealArrayType`, `ComplexArrayType`, …) or a shape-typed alias beside its producing class, like `DiffractionPatterns` in [api/diffraction.py](src/ptychodus/api/diffraction.py). A dtype-preserving helper takes a `TypeVar` bound to `numpy.ndarray`; where no dtype is promised (dtype branching, file-format boundaries) use `AnyArrayType`. Write abstract scalars bare: `numpy.floating`, not `numpy.floating[Any]`. [tests/test_api_array_annotations.py](tests/test_api_array_annotations.py) enforces this in `api/`, since numpy's defaulted stubs never trip mypy's `disallow_any_generics`.
- **numpy → Python scalar in `api/`.** Cast only at the boundary — the `return` of a function annotated `-> float`/`-> int`/`-> bool`, or assignment to a Python-typed dataclass field. Everywhere else let numpy scalars propagate through arithmetic. When you do cast, use the constructor (`float(...)`, `int(...)`, `bool(...)`, `complex(...)`), never `.item()` — mypy sees the target type, and it matches the HDF5-read pattern in [io.py](src/ptychodus/api/io.py).
- **Underscore-prefixed names in `api/`.** A name is public iff production code outside `api/` uses it **or** its module's `__all__` lists it; everything else, helpers shared within `api/` included, is `_`-prefixed and renamed on promotion. Tests are exempt. Rather than import another module's underscore name, move the logic onto a peer method of the shared abstract base, as `BinningStep.apply_to_dtype` does. Audit with `rg -Un --pcre2 'from ptychodus\.api\.[\w.]+ import (\([^)]*\b_|_)' src/ scripts/` — `-U` catches the parenthesized form.
- **Pipeline steps declare their dtype effect.** A `DiffractionPrepStep` whose `apply()` widens value range (summing, scaling, accumulating) overrides `apply_to_dtype(dtype)` to return a dtype holding the result, and `apply()` produces it — typically `numpy.sum(..., dtype=self.apply_to_dtype(data.dtype))`. Sister of `apply_to_extent` and `apply_to_pixel_geometry`; default identity. Pre-sized buffers fold it via `compute_assembled_dtype` (the pipeline's `compute_output_dtype`, then `DetectorCorrections.apply_to_dtype`), wide enough by construction, not by `isinstance`. An additive per-pixel map follows `apply_to_pixel_map`, overridden where a map must not take the pattern path.
- **Tunables are keyword arguments, not module constants.** A threshold, tolerance, epsilon or floor that changes what a function returns is keyword-only with a default (`def compute_probe_overlap(product, *, roundoff_floor: float = 1.0e-12)`), documented in the docstring, defaulted on the public entry point so private helpers don't repeat the literal. The test: could a caller plausibly want another value? Private module constants remain only for values callers must not vary — data tables (`_FLUORESCENCE_LOAD_PATHS`), precompiled objects (`_UNSAFE_PATH_CHARS`), mathematical invariants (`_AFFINE_MINIMUM_POINTS`).
- **A private constant lives in the narrowest scope that reads it** — inside the one function or method that reads it, or on the one class; module scope is for values two or more share. Exceptions: tunables are keyword arguments (above), and the `*_ENTRY` subprocess entry-point strings stay at module scope because [tests/test_subprocess_entry_points.py](tests/test_subprocess_entry_points.py) finds them by AST-scanning module-level assignments — inlining one silently drops it from that guard.
- **Classmethods vs free functions in `api/`.** Alt-constructors use `@classmethod`: `Cls.from_X(x, ...)` for data-taking factories (`Interval.from_bounds`), `Cls.create_X()` for parameterless well-known instances (`DiffractionMetadata.create_null`); domain-verb names (`PluginRegistry.load_plugins`) mark a side effect `from_*` doesn't convey. Avoid `@staticmethod` — helpers touching neither `self` nor `cls` go to module scope, `_`-prefixed when private. Per-object analyzers returning a small dataclass are free `compute_*`/`estimate_*` functions in the activity-verb module ([metrics.py](src/ptychodus/api/metrics.py), [preprocess/](src/ptychodus/api/preprocess/)), even when the dataclass lives elsewhere.
- The `webapp/ui/` frontend is TypeScript compiled to native ES modules by plain `tsc` — no bundler, framework or runtime npm deps. The gitignored `ui/dist/` ships in the sdist and wheel via `[tool.setuptools.package-data]`, so a PyPI install never needs Node. [setup.py](setup.py) compiles it from **both** the `sdist` and `build_py` cmdclasses — `build_py` alone leaves the tarball without a UI. A missing `tsc` warns and builds without the UI; `PTYCHODUS_WEBAPP_REQUIRE_UI_BUILD=1` (release builds) makes it fatal.
- **`cli/` versus `scripts/`.** `src/ptychodus/cli/` holds the `[project.scripts]` modules and shared argparse/logging helpers, ships in the wheel, and stays free of optional-extra imports; a new console command goes there with an entry point. The top-level `scripts/` is **not** packaged — checkout-run one-off and facility tooling. The `ptychodus-reconstruct-<beamline>` drivers are short `InstrumentProfile`s over `_reconstruct_standard.py`, all but `reconstruct_pear.py` (JSON parameters) and `reconstruct_batch_lamni.py` (YAML settings, multi-GPU). `--prepare-only` writes a prepared directory (`diffraction.h5`, `product.h5`, aligned `ptychi_options.yaml`) for `ptychodus-reconstruct` (`reconstruct_prepared.py`), which replaces the deprecated `ptychodus-bdp`. `reconstruct_subprocess.py` is a pipe-driven child, unrelated to `plugins/ptychi/_subprocess.py`.
- **PyTorch comes from a pinned index, chosen by extra.** `ptychi` installs a CPU torch and each `ptychi-cuda*` extra the matching CUDA build, mirroring the CUDA versions `scripts/podman/build` targets; `[tool.uv.sources]` in [pyproject.toml](pyproject.toml) pins them and `[tool.uv] conflicts` keeps them exclusive. Only uv honors this — `pip install ptychodus[ptychi]` takes PyPI's default CUDA torch, which is why [containers/](containers/) install their own first. A build newer than the driver's CUDA ceiling silently runs on the CPU; `ptychodus-system-check --require-cuda` gates that.
- **All documentation is Markdown.** `docs/source/*.md` is MyST, parsed by `myst_parser`; no reStructuredText remains and no new `.rst` should be added. Sphinx constructs use MyST directive fences — ` ```{note} `, ` ```{toctree} ` — with `:option: value` lines directly under the opening fence and a blank line before directive content. Autodoc stanzas stay raw reStructuredText inside ` ```{eval-rst} ` blocks. Roles use MyST syntax: `` {py:class}`…` ``, `` {ref}`…` ``. Enabled MyST extensions are declared in [docs/source/conf.py](docs/source/conf.py).
- **Markdown style** — `uv run pymarkdown scan $(git ls-files '*.md')` enforces part; the rest is house convention: ATX headings, one H1 per file, `###` max outside `docs/source/` (MyST may use `####`); backtick fences tagged `sh`, not `bash`; `-` bullets, ordered lists numbered for real; inline repo-relative links, bare URLs as `<https://…>`; pipe tables with outer pipes and an unpadded `| --- |` separator; **no hard wrapping**; `**bold**` for identifiers, paths and warnings, backticks for code, em dash `—` for asides; YAML front matter only in `.claude/skills/*/SKILL.md`. Nested content indents to the parent's content column — 3 spaces under an ordered marker, 2 under a dash.

## Repository

CI targets `main`; local dev branches (e.g. `amsc`, `webservice`) are active — confirm the intended target before opening PRs.

**Never commit without being asked.** Finish the work, run the gate, and leave the changes in the working tree — staged if asked, unstaged otherwise. Neither an approved plan that describes commits, nor a clean gate, nor a long task with natural checkpoints is permission to write history; say what is ready and let the commit be a separate instruction. The same goes, more so, for `git push`, `git commit --amend`, `git reset`, force-pushing, and opening or updating PRs.
