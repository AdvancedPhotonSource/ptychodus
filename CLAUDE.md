# CLAUDE.md

## Project

Ptychodus is a ptychography data-analysis application that ingests instrument data, prepares it for processing, and dispatches it through pluggable reconstruction libraries (PtyChi, PtychoPINN, and others). It runs as a PyQt5 GUI, headless CLI commands, and a streaming processor inside beamline pipelines (pvapy area-detector). Python ≥3.11, `uv` preferred.

## Common Commands

```sh
uv sync --extra globus --extra gui --extra ptychi   # dev install; ptychi is CPU torch
uv sync --extra globus --extra gui --extra ptychi-cuda130  # GPU: match nvidia-smi's CUDA ceiling
uv run ptychodus                                    # GUI
uv run ptychodus-reconstruct -i <in> -o <out>       # headless — any library, over a prepared directory
uv run pytest                                       # tests
uv run pytest -m browser tests/webapp/browser       # web UI in system Chrome; tsc first
uv run ptychodus-agent serve                        # agent service (agent extra); PTYCHODUS_AGENT_*
uv run ruff check . && uv run ruff format --check . # lint + format
uv run mypy src/ptychodus scripts tests             # types (wider than CI's)
```

Container builds: `scripts/podman/build` (Dockerfiles in [containers/](containers/); tags `ptychodus:<version>-<variant>` over the script's `DEFAULT_VARIANTS` — CPU, each supported CUDA, ROCm, XPU). Release images install the PyPI release named by `PTYCHODUS_VERSION` (default: latest) over their base image's device-specific torch; `Dockerfile.dev` (variant `dev`, on request) installs the checkout and backs the devcontainer. Libraries on no index (PtychoPINN and others) get wheels built from sibling checkouts. The launcher `scripts/podman/ptychodus` picks the GPU family and, on NVIDIA, the newest release built for a CUDA variant the driver supports, then the newest such variant. Docs: `make -C docs html`.

Other entry points (`ptychodus-reconstruct`, `ptychodus-webapp` and the rest) are in [pyproject.toml](pyproject.toml) `[project.scripts]`, with modules in [src/ptychodus/cli/](src/ptychodus/cli/) — but for the two services, `ptychodus-webapp` and `ptychodus-agent`, whose `cli.py` lives in their own package. Unpackaged operator tooling — the podman wrapper, the per-facility HPC token/submit helpers — lives in the top-level [scripts/](scripts/) and runs from a checkout, e.g. `python scripts/genesis/ptychodus_iri_tokens.py`.

### Testing

Tests cover `api/`, `model/`, `view/widgets/` and the Qt-free `controller/rendering/` (tested at `tests/` root, on a bare install), plus the two `controller/` modules with real logic: [controller/parameters.py](src/ptychodus/controller/parameters.py) (unit conversion, signedness inference, complex amplitude/phase editing) and [controller/processing/generated.py](src/ptychodus/controller/processing/generated.py), the mostly pure `Sequence[DescribedField] -> list[_Item]` pipeline laying out each library's panel. A reusable widget with logic of its own belongs in `view/widgets/`, like `DecimalRangeSlider`. **Do not add tests for anything else under `view/` or `controller/`**, controller helper functions included. [tests/conftest.py](tests/conftest.py) drops `tests/view/`, `tests/controller/`, `tests/webapp/` and `tests/agent/` via `collect_ignore` when their extra is missing (`tests/agent/` also when `tests/webapp/` is dropped, since it runs the agent against the real webapp), and hosts the session-scoped `qapp` fixture, which imports `QApplication` inside so the conftest imports on a bare install. `pytest tests/` must pass on a bare `pip install .` (what CI runs), so nothing reachable from `ptychodus.model` at import time may need an optional dependency — an optional subsystem defers its import, as a reconstruction library does inside `_build()`. Guard a test that needs an optional library with `pytest.importorskip('ptychi')`; drop an optional-extra directory with `collect_ignore` in the conftest — `importorskip` there is reported as an error, not a skip.

**Web UI tests.** [tests/webapp/test_ts_route_parity.py](tests/webapp/test_ts_route_parity.py), in the normal suite, holds every URL `ui/src/api.ts` builds to a route and to that route's declared query parameters — the service ignores an undeclared one and answers 200. [tests/webapp/browser/](tests/webapp/browser/) drives the served UI in a real browser through pytest-playwright (dev group), in the system Chrome where there is one; `addopts` deselects its `browser` marker, so it runs only under `-m browser`, and it fails rather than compiles when `ui/dist/` is older than `ui/src/`, so run `tsc` first. Each browser test seeds a storage root, serves it with [tests/webapp_ui_fixtures.py](tests/webapp_ui_fixtures.py), and ends with `ServedPage.assert_clean`, which fails on an uncaught exception, an unexpected error status, or a request no route declares.

## Architecture

### Three-layer separation: api / model / view+controller

- **`src/ptychodus/api/`** — pure-Python, stateless domain layer: core data structures (`Product`, `ProbeEnsemble`, `Object`, `ProbePositionSequence`, `DiffractionDataset`, `AssembledDiffractionData`), abstract interfaces (`DiffractionFileReader/Writer`, `ProductFileReader/Writer`, `Reconstructor`, `TrainableReconstructor`), and `PluginRegistry` with its read-only `PluginCatalog`s. Module names follow SciPy: activity verbs for operations (`interpolate`, `reconstruct`, `propagate`, `simulate/` for forward models, `preprocess/` for preprocessing pipelines, and `processing`, a run of any of them — `RunState`, `RunRecord` — a gerund because `process` would read as an operating-system process), plural collections for infrastructure (`plugins`, `constants`, `typing`), singular nouns for domain types (`affine` owns `AffineTransform`, its decomposition and its estimator, math only; the product-level correction is `product.transform_product`, and the Bragg/Laue exit frame is the `scattering/` package). It depends on nothing else in ptychodus and holds no application state — observers, parameters, settings and plugin selection live in `model/`. [tests/test_layering.py](tests/test_layering.py) fails on any import from `api/`, `plugins/` or `webapp/` into `model`, `view` or `controller`.
- **`src/ptychodus/model/`** — application logic behind the GUI, which `__main__.py` starts. Most subpackages (`diffraction/`, `product/`, `processing/`, `fluorescence/`, `analysis/`, `globus/`, `genesis/`, and others) expose a `*Core` class owning their settings, repositories and APIs; reconstruction libraries expose a `*ReconstructorLibrary` instead and live under `plugins/`, discovered rather than composed. `model/core.py::ModelCore` is the composition root, constructing them all in dependency order.
- **`src/ptychodus/view/`** (PyQt5 widgets, no logic) and **`src/ptychodus/controller/`** (mediates widgets↔model) mirror the model layout, with composition roots `view/core.py::ViewCore` and `controller/core.py::ControllerCore`; the navigation toolbar order in `ViewCore` is the source of truth for left/right stacked-panel indexes. `controller/rendering/` is not mediation but Qt-free array-to-color transformation (`VisualizationEngine` and its renderers); only the GUI drives it, so `ControllerCore` builds every engine and no `*Core` holds one. Three `__init__.py` files are deliberately empty and say why — `controller/` keeps `controller/rendering/` importable without PyQt5, `controller/diffraction/` breaks an import cycle with `controller/product/`, and `api/scattering/` keeps its numpy-only `geometry` importable by `diffraction` and `product` without pulling in `frame` — so import both composition roots from their `core` modules, and scattering names from their submodule.

The GUI is optional: `__main__.py` starts it and needs PyQt5, and headless work runs through the `ptychodus-*` commands, which build no `ModelCore`. `ptychodus-stream` ([cli/stream.py](src/ptychodus/cli/stream.py), the `stream` extra) is a third entry mode: a pvapy area-detector processor that estimates the probe (average pattern) and object (STXM-DPC) while a scan streams, saves each scan to a storage root, and, when its configuration names a library's algorithm, reconstructs each finished scan on a thread of its own for PVs only. Its pvapy-free core, [cli/_stream.py](src/ptychodus/cli/_stream.py), imports no `ptychodus.model`, as [tests/test_layering.py](tests/test_layering.py) enforces.

### Index-based pattern/position association

Diffraction patterns and probe positions are paired by **integer scan index**, never by array order. This is what makes streaming and mismatched-rate ingest robust.

- Producers: `DiffractionArray.get_indexes()` (`api/diffraction.py`); `ProbePosition.index` (`api/probe_positions.py`).
- Matcher: `interpolate_at_indexes` in `api/interpolate.py` is the rule's home; `prepare_reconstruct_input(assembled_data, product, ...)` in `api/reconstruct.py`, the STXM-DPC object generator and `ptychodus-stream` all pair through it. Pattern indexes are authoritative — duplicate position indexes are averaged into anchors, pattern indexes inside the anchor range without an exact position are linearly interpolated, and those outside it are dropped (no extrapolation). `match_at_indexes` beside it is the exact-match variant for comparing two position sets (`ProbePositionSequence.match_indexes`, the affine estimator, `ptychodus.api.analyze`): duplicates average the same way, and an index missing from either side is left out, never imputed.
- Round-trip: HDF5 and CXI product writers persist position indexes via `ProductFileKeys.PROBE_POSITION_INDEXES` and `CXIFileKeys.PROBE_POSITION_INDEXES`.
- Line-major indexes: when a positioner records more points per scan line than the detector, a running count on either side slides the pairing by the surplus, line by line, yet every pattern still finds a match. A registration passing `line_index_stride` to `MDAPositionFileReader` or `APS2IDDiffractionFileReader` instead numbers a point `line * RASTER_LINE_INDEX_STRIDE + column` (`plugins/mda/mda_position_file.py`), so the unchanged matcher leaves surplus commanded points unclaimed, lets a short line claim fewer, and drops a detector line past the end of the positioner record. The default numbering is untouched.

### Pixel origins

Probe arrays and detector frames share the FFT bin origin, pixel `N // 2` of each axis (the middle pixel on an odd one): a probe's beam axis sits there, as a detector's DC pixel does, so `fftshift(fft(ifftshift(x)))` carries one to the other with no phase ramp. `ProbeGeometry.get_transverse_coordinates` measures from it, every probe generator centres on those coordinates, and `resolve_patch_bounds` places that pixel on the probe position. Object arrays are located differently: `ObjectCenter` is the world position of pixel `(N - 1) / 2`. Every reconstruction library registers a position to the probe's midpoint instead, so each adapter converts with `axis_offset_x_px`/`axis_offset_y_px` (0.5 on an even axis, 0 on an odd one) at its boundary — pty-chi through `_to_ptychi_positions_px` and its `position_origin_coords`, cdtools through `min_translation`, the PEAR reader on load. Detector flips reflect about the DC pixel, and a crop centres the beam on it.

### Bragg and Laue geometry

A product's positions, probe and object are in the exit frame of its `ProductMetadata.scattering_geometry` (`api/scattering/geometry.py`), which is the ordinary transmission frame when the geometry is forward. Lab-frame data is carried in exactly once, where it enters a product — position builds, model probes, the `offers_scattering_geometry` CLI drivers — and each of those resolves the map through `api/scattering/frame.py::resolve_exit_frame_transform`, which falls back to the identity with a warning where the exit frame is undefined (near field, a grazing beam); reconstructor output and loaded products are already in it. Guide: [docs/source/bragg_laue.md](docs/source/bragg_laue.md).

### Plugin system

`api/plugins.py::PluginRegistry.load_plugins()` walks `ptychodus.plugins.*` with `pkgutil.iter_modules` and calls each module's `register_plugins(registry)`. Module-load failures are logged and skipped — this is how optional-dependency plugins (LCLS, NSLS-II, …) silently disable themselves. Never make plugin loading fatal.

**Registration in `api`, selection in `model`.** Plugin modules register into each registry field's `PluginList`; `load_plugins` freezes them into read-only `PluginCatalog`s — sorted by display name, looked up by either name — and a late `register_plugin` warns and is skipped. The current selection lives in `model/plugins.py::PluginChooser`, an `Observable` over one catalog. `ModelCore` wraps each catalog a core selects from **once** and hands that chooser to every consumer: a settings-backed `PluginChooserParameter` and a dialog's `FileTypeChooser` share it, and a second wrap would hold an independent selection. Lookup-only categories — generators, probe presets, training-data writers — are passed as catalogs. A chooser does not see later registrations, so finish a self-made `PluginList` before wrapping it.

**A file handler names itself.** Every reader and writer interface is a one-line subclass of `api/files.py::FileReader[T]` or `FileWriter[T]`, whose `FileHandler` base builds the Qt name filter `get_file_filter()` from the abstract `get_file_description()` and `get_file_extensions()` — extensions carry a leading dot to compare against `Path.suffix`, and are sorted so the filter is stable. `register_plugin` derives `display_name` from that filter, so a file-handler registration passes only `simple_name`; `display_name` is for plugins that are not file handlers (generators, presets, fluorescence enhancers, reconstructor libraries, language-model providers). Either mistake warns and is skipped rather than raising, because `load_plugins` catches only `AttributeError`. A class serving several instruments takes its description as a constructor argument rather than being registered twice under one instance.

### Settings & observers

Settings flow through `model/parameters.py::Parameter[T]` and `ParameterGroup`: each `*Core` calls `settings_registry.create_group(name)` and creates typed parameters, and `model/settings.py::SettingsRegistry` serializes the tree as INI. React to changes by hooking `Observer`/`Observable` (`model/observer.py`) rather than polling. `model/plugins.py::PluginChooserParameter` adapts a `PluginChooser` into a settings-backed `Parameter[str]`, the typical bridge from settings string to selected plugin; the reconstructor selection is two in series — a library from the chooser, then an algorithm resolved against that library.

**Three idioms, and which to reach for.** A hand-written `*Settings` class backs every subsystem and is what a new `*Core` writes. The other two start from a pydantic object — `Reconstructor.get_default_options()`, `ProbePositionsGenerator.get_default_options()` — and differ in who wrote it.

A declaration **ptychodus owns** is read straight by `model/declared.py`: `describe()` takes bounds, choices and display text off each `Field` and spells its key from the field name (PascalCase, unit suffixes in words, an optional `prefix` for one of several like branches); `declare_in()` creates the live parameters and `restore()` writes them back. No policy, overlay or table. A new declaration uses this, as the scan-pattern, probe- and object-generator plugins, the fluorescence enhancers, cdtools and PtychoPINN do.

A declaration **ptychodus does not own** cannot be annotated at the source, so `model/processing/flatten.py` projects it and a per-library table supplies what upstream omits — display text, bounds, choices, renamed keys, adapters bridging one field onto several. pty-chi is why it exists. **Transitional**: it retires with the Qt panels.

Both reach the GUI and the reconstruct path through `ProcessingParameterStore` — `register_declared` for the first, `register` for the second. The fluorescence enhancers' branch table lives in `model/fluorescence/core.py`; each enhancer persists in its own group and lays out with the same generated panels. All three idioms owe this: a parameter states its bounds where it is declared, because `controller/parameters.py` raises on a missing one rather than degrading, and infers signedness from the minimum.

### Standard HDF5 layout (external interface — change carefully)

`api/io.py::StandardFileLayout` is the contract for the reconstruct, train and enhance commands and the remote workflows: `diffraction.h5`, `product.h5`, `fluorescence.h5`, a `model` stem whose extension the trainable reconstructor supplies, and per action an options document and a log — `reconstruct_options.yaml` / `reconstruct.log`, `train_options.yaml` / `train.log`, `enhance_xrf_options.yaml` / `enhance_xrf.log`. An options document names what it configures (library and algorithm, or an enhancer as `algorithm`) beside the library's own pydantic options; [api/options.py](src/ptychodus/api/options.py) writes the canonical form and reads one back onto the defaults. A log is appended to, never replaced. Input versus output is the containing directory (the commands' `-i`/`-o`; remote workflows stage under `<workflow_root>/input/` and `<workflow_root>/output/`). The enum's `path(directory)`, `checkpoint_path(directory, progress)` and `rank_path(directory, rank)` helpers build paths — `<stem>.<progress:06d><suffix>`, a checkpoint: the immutable result at one progress value, and `<stem>.rank<NN><suffix>`, one log per process of a multi-process launch. Key names, which external consumers depend on, live in `DiffractionFileKeys` / `ProductFileKeys`; CXI paths in `CXIFileKeys`, with `CXIVariant` choosing a writer's layout — readers detect it and take no variant.

`api/storage.py` is the storage-root contract: `<root>/<kind>/<uuid>/` folders, each a `manifest.json` and the HDF5 file it names, linked by `derived_from` and grouped by campaign. The webapp reads it. Every resource is written in place and published by its manifest: the folder is created exclusively, its files are written and `fsync`ed, and `save_manifest` writes the manifest last and atomically, so a folder without one is no resource to any reader. The chainable savers (`save_campaign_resource`, `save_diffraction_resource`, `save_product_resource`, `save_fluorescence_resource`, and `save_prepared_resources` for a diffraction resource with its product) publish once and return the uuid the next saver takes; the fluorescence saver always writes XRF-Maps' NNLS paths. A processing run writes a run resource — a product or fluorescence resource whose manifest carries `run` — published at the start by `start_run` — its folder is the run's `StandardFileLayout` output directory — and advanced by `commit_checkpoint` and `finish_run`, each replacing the manifest with `files[kind]` naming the newest checkpoint or the final file; `ptychodus-reconstruct --product <uuid>` (which refuses `-o`) and `ptychodus-enhance-xrf` given uuids write this way. Every resource a processing command produces carries the manifest's typed `run` field, an `api/processing.py::RunRecord` (state and reason, progress against a goal, command, version, user, options document, `updated_at`, and the job id and model URI of a run a job started); imported data — what `ptychodus-import` publishes from prepared files — has none and records nothing of its source. A product may name its options document as `files['options']` (a run's result, or an imported prepared directory's), and `resolve_storage_inputs` returns it, which `ptychodus-reconstruct --product` uses unless given `--options`. Resources are named by uuid alone, and a reader never assumes a file name: `resolve_resource_file` follows the manifest to a resource's current data, and `resolve_storage_inputs` to a stored product's inputs.

### Reconstructor libraries

Each reconstruction library exposes a `*ReconstructorLibrary`; the base in [api/reconstruct.py](src/ptychodus/api/reconstruct.py) owns everything but what the library builds. A subclass passes `requires=` — the modules it cannot work without — and implements `_build()`. The base resolves those names without importing them (`is_available()`), calls `_build()` once on first `__iter__`, and logs through the library's own logger: the version on success, `<distribution> not found.` at INFO when the modules are absent, and a **warning** with traceback when they resolve but `_build()` raises `ImportError` — a fault, not an uninstalled library. So a library writes no availability logic and never imports its dependency at module scope. A library is named where it registers; the section table and parameter store key on that name. The surface is stable whether or not the library is installed, so `ModelCore` hands `ProcessingCore` the whole chooser and `ProcessingCore` answers which libraries are in play. Reconstructors yield `ReconstructOutput` per iteration so the GUI can stream progress.

**Process isolation is the application's, not the plugin's.** A reconstructor or fluorescence enhancer is a plain picklable object whose `reconstruct` / `train` / `enhance` is an ordinary generator, leaves `self` unchanged and imports its framework inside the method. The background tasks in `model/processing/monitor.py` and `model/fluorescence/monitor.py` run it through `api/spawn.py::iterate_in_subprocess` — a `functools.partial` over the bound method, pickled to a spawned child under `DeviceSelection.environment()` — so the GUI process never holds a GPU context. Training reports the trained model it wrote in `TrainOutput.trained_model`, and the caller loads it. The one-shot CLIs (`ptychodus-reconstruct` and the drivers, `ptychodus-train`, `ptychodus-enhance-xrf`) and `ptychodus-stream` call the plugin in-process. A declared options model must survive an options document and pickling with its values, concrete types and set fields, and forbids undeclared fields — [tests/test_options_round_trip.py](tests/test_options_round_trip.py) checks every registered library.

**A library reconciles conventions at its own boundary.** ptychodus stores a probe in photons per pixel — `sum|P|^2` is the photons incident per exposure, so an energy-conserving propagator gives a detector sum of `sum|P*O|^2` — and probe positions in meters. A library whose forward model or coordinate frame differs converts on the way in and applies the inverse to every yielded `ReconstructOutput`, so a stored product is in ptychodus's convention whatever produced it, and one library's output is another's warm start. Measure the scale against the library's own forward model rather than hardcoding it — pty-chi's normalization differs between far and near field.

### Remote compute

Both providers are optional-dep gated but constructed by `ModelCore` even when disabled:

- `model/globus/` — Globus Compute (original APS workflow).
- `model/genesis/` — IRI/AmSC HPC via `facility_adapters.py`, with per-facility scripts under `scripts/genesis/{alcf,nersc,olcf}/`.

Neither runs the application remotely. `ProcessingAPI.stage_reconstruct_inputs` / `stage_train_inputs` stage a `StandardFileLayout` directory from the GUI's selection — the options as a document — and the remote side runs `ptychodus-reconstruct` or `ptychodus-train` over it.

### Integrated agent service

`src/ptychodus/agent/` is the integrated agent, run as `ptychodus-agent` from the `agent` extra, which also carries pydantic-ai. It streams to the web UI's chat drawer over AG-UI and keeps each user's conversations private. Like the webapp, it imports only `ptychodus.api` and `ptychodus.plugins`, and the two services never import each other — both enforced by [tests/test_layering.py](tests/test_layering.py). Configuration is `PTYCHODUS_AGENT_*` pydantic-settings ([agent/config.py](src/ptychodus/agent/config.py)), never the INI registry. Deployment: [src/ptychodus/agent/README.md](src/ptychodus/agent/README.md).

- **Language models.** A `LanguageModelProvider` plugin ([api/language_model.py](src/ptychodus/api/language_model.py), implementations in [plugins/language_models/](src/ptychodus/plugins/language_models/)) is a service hosting language models, not a language model. It resolves a model ID to a `LanguageModelEndpoint` (wire protocol, base URL, model ID, key): plain data, so providers assume no agent framework and import no LLM SDK. [agent/endpoint.py](src/ptychodus/agent/endpoint.py) is the one adapter onto pydantic-ai, resolving the one deployment-wide endpoint at startup with the provider's options applied by `api/options.py::apply_options_document`; swapping frameworks replaces it and `loop.py`, never a provider. Instruments often have no internet access, so a provider touches the network only in `list_models()` — never at import, registration or `resolve()`. Credentials come from environment variables, never settings, and go only to an https or loopback URL.
- **Tools are the webapp's MCP server**, the same surface outside agents use. [agent/loop.py](src/ptychodus/agent/loop.py) builds an `MCPToolset` that sends the service's token and, as `X-Ptychodus-User`, the user of each turn, and passes the server's instructions to the language model. Images from earlier turns reach the language model only as notes (`history.py`).
- **Users.** The service believes the header `PTYCHODUS_AGENT_USER_HEADER` names, which the facility's proxy sets after sign-in, so only the proxy may be able to reach it. Every store read and write is keyed by that user.
- **A turn** is one prompt and the agent's answer, run through pydantic-ai's AG-UI adapter with the server holding the history ([agent/app.py](src/ptychodus/agent/app.py)). Only a completed turn is saved; every turn, however it ends, writes a row to the audit log in [agent/store.py](src/ptychodus/agent/store.py) and one INFO line. Per-turn usage limits and a per-user daily token limit bound a shared quota. A conversation runs one turn at a time, tracked in memory, so the service is one process.
- **Rendering.** Markdown and `$`-delimited LaTeX become HTML on the server ([agent/rendering.py](src/ptychodus/agent/rendering.py)): markdown-it-py, `dollarmath`, latex2mathml, then nh3 against an allowlist of basic HTML and MathML. latex2mathml escapes nothing, so the sanitizer runs last on everything. [agent/events.py](src/ptychodus/agent/events.py) sends each text message's HTML in a `ptychodus.rendered_text` CUSTOM event as each block completes, with its source length in UTF-16 code units, and strips binary content from tool results; the drawer inserts no other HTML, and draws `render_*` calls itself through the webapp's REST image routes ([ui/src/chat/render_calls.ts](src/ptychodus/webapp/ui/src/chat/render_calls.ts), held to the MCP tools by [tests/webapp/test_ts_render_calls.py](tests/webapp/test_ts_render_calls.py)).

### ptychodus.webapp service

`src/ptychodus/webapp/` is the read-only webapp, run as `ptychodus-webapp` from the `webapp` extra. It reads only from `ptychodus.api` (its storage layout and manifests are `api/storage.py`, shared with the writers) and **must not import `ptychodus.model`, `ptychodus.view` or `ptychodus.controller`** — enforced by [tests/test_layering.py](tests/test_layering.py) — and nothing outside it imports it, so a bare install never touches its dependencies. Surface: FastAPI REST under `/api/v1/*`, MCP server at `/mcp`, minimal TypeScript UI at `/ui/`, SQLite metadata cache reconciled by a watchdog observer. Composition root: `create_app()` in `app.py`. Deployment: [src/ptychodus/webapp/README.md](src/ptychodus/webapp/README.md).

REST routes and MCP tools are thin transports over one service, `service/resources.py::ResourceService`, whose every method declares an operation class with `@operation`: **instant** reads the metadata cache; **bounded** also reads resource files — renders and the `api/analyze.py` reports — in a worker thread under the shared `RenderRunner` cap. It refuses with `service/errors.py`'s `ResourceNotFoundError` or `InvalidRequestError`, which REST answers as 404 or 400 and MCP as a `ToolError` with the same text. A route states the class as `x-operation-class`, a tool at the end of its description, and [tests/webapp/test_rest_mcp_parity.py](tests/webapp/test_rest_mcp_parity.py) holds each pair to the same parameters, data, refusals and class. Every tool carries read-only annotations, and the server's instructions are its domain prompt. MCP authenticates bearer tokens against the owner-only file `PTYCHODUS_WEBAPP_MCP_TOKENS_FILE` names, which holds only SHA-256 digests and which `ptychodus-webapp mint-token` writes. Without it, `create_app()` refuses to start unless `PTYCHODUS_WEBAPP_MCP_ALLOW_UNAUTHENTICATED` serves MCP to every caller, for development only. Each tool call is logged with the token's client and, when the client sends one, the user its `X-Ptychodus-User` header names — that client's claim, authorizing nothing. A render tool returns its scales as a JSON text block beside the PNG as well as structured content, since pydantic-ai, like other clients, drops structured content from a result holding an image.

## Conventions

- Ruff: **single-quoted** strings, 100-char lines, py311 target. Enabled rules: F, N, NPY, TID251.
- Preserve unit suffixes on physical quantities (`probe_energy_eV`, `set_value_from_string`) — silence naming lints with `# noqa: N802/N806/N815`, don't rename.
- **Angles and π.** A user-facing geometric angle is `_deg` and a phase is `_rad`; nothing is stored in turns, which the GUI angle editor offers only as a display unit. π is spelled only `PI`, `TWO_PI` or `TWO_PI_J` from [api/constants.py](src/ptychodus/api/constants.py), other multiples as arithmetic on them (`0.5 * PI`). Convert a scalar with `math.radians`/`math.degrees` and an array with `numpy.deg2rad`/`numpy.rad2deg`. Ruff's TID251 `banned-api` in [pyproject.toml](pyproject.toml) rejects `numpy.pi`, `math.pi`, `numpy.radians` and their kin everywhere but `api/constants.py`.
- Type hints are mandatory. `pyproject.toml` lists modules whose missing stubs are intentionally ignored — keep new code typed and don't widen that list.
- `ModelCore.is_developer_mode_enabled` is `True` when the effective log level ≤ DEBUG (`--log-level 10`); some controllers gate features (probe-position analysis, the product visualization view) behind it.
- HTTP-client code uses `httpx` throughout (sync `httpx.Client` for repeated calls, module-level `httpx.get/post` for one-shots). `requests` is not a dependency.
- **No hand-rolled pickling.** An object crosses a process boundary as itself, never as `pickle.dumps` bytes, on the `SimpleQueue` [api/spawn.py](src/ptychodus/api/spawn.py) hands the child. `SimpleQueue.put` pickles synchronously, so a later in-place edit cannot tear the array and an unpicklable message fails at its own `put` as `ChildError`, not silently on `multiprocessing.Queue`'s feeder thread. The one explicit pickle is `send_error`'s, so an unrebuildable exception costs only `child_exception`. Persisted data never pickles (`numpy.load`/`savez` keep `allow_pickle=False`, `torch.load` takes `weights_only=True`); a test may, to pin transport survival.
- Prefer affirmative conditionals when both branches do meaningful work — `if x.is_file(): ... else: ...`, not the negated form. Guard clauses that early-return are still idiomatic.
- **No forward references in comments.** A comment or docstring explains what the code guarantees, not who consumes it. Naming a caller is wrong the moment one is added, moved or renamed. In `api/` it is worse than stale: naming a `model/` or `cli/` symbol inverts the layering the package exists to enforce, even in prose. Describing what the code itself depends on is fine — an import already states it.
- **Array annotations name a dtype.** Bare `numpy.ndarray` and `numpy.dtype` mean `Any` while looking annotated. Use a dtype-family alias from [api/typing.py](src/ptychodus/api/typing.py) (`RealArrayType`, `ComplexArrayType`, …) or a shape-typed alias beside its producing class, like `DiffractionPatterns` in [api/diffraction.py](src/ptychodus/api/diffraction.py). A dtype-preserving helper takes a `TypeVar` bound to `numpy.ndarray`; where no dtype is promised (dtype branching, file-format boundaries) use `AnyArrayType`. Write abstract scalars bare: `numpy.floating`, not `numpy.floating[Any]`. [tests/test_api_array_annotations.py](tests/test_api_array_annotations.py) enforces this in `api/`, since numpy's defaulted stubs never trip mypy's `disallow_any_generics`.
- **numpy → Python scalar in `api/`.** Cast only at the boundary — the `return` of a function annotated `-> float`/`-> int`/`-> bool`, or assignment to a Python-typed dataclass field. Everywhere else let numpy scalars propagate through arithmetic. When you do cast, use the constructor (`float(...)`, `int(...)`, `bool(...)`, `complex(...)`), never `.item()` — mypy sees the target type, and it matches the HDF5-read pattern in [io.py](src/ptychodus/api/io.py).
- **Underscore-prefixed names in `api/`.** A name is public iff production code outside `api/` uses it **or** its module's `__all__` lists it; everything else, helpers shared within `api/` included, is `_`-prefixed and renamed on promotion. Tests are exempt. Rather than import another module's underscore name, move the logic onto a peer method of the shared abstract base, as `BinningStep.apply_to_dtype` does. Audit with `rg -Un --pcre2 'from ptychodus\.api\.[\w.]+ import (\([^)]*\b_|_)' src/ scripts/` — `-U` catches the parenthesized form.
- **Pipeline steps declare their dtype effect.** A `DiffractionPrepStep` whose `apply()` widens value range (summing, scaling, accumulating) overrides `apply_to_dtype(dtype)` to return a dtype holding the result, and `apply()` produces it — typically `numpy.sum(..., dtype=self.apply_to_dtype(data.dtype))`. Sister of `apply_to_extent` and `apply_to_pixel_geometry`; default identity. Pre-sized buffers fold it via `compute_assembled_dtype` (the pipeline's `compute_output_dtype`, then `DetectorCorrections.apply_to_dtype`), wide enough by construction, not by `isinstance`. An additive per-pixel map follows `apply_to_pixel_map`, overridden where a map must not take the pattern path.
- **Tunables are keyword arguments, not module constants.** A threshold, tolerance, epsilon or floor that changes what a function returns is keyword-only with a default (`def compute_probe_overlap(product, *, roundoff_floor: float = 1.0e-12)`), documented in the docstring, defaulted on the public entry point so private helpers don't repeat the literal. The test: could a caller plausibly want another value? Private module constants remain only for values callers must not vary — data tables (`_FLUORESCENCE_LOAD_PATHS`), precompiled objects (`_UNSAFE_PATH_CHARS`), mathematical invariants (`_AFFINE_MINIMUM_POINTS`).
- **A private constant lives in the narrowest scope that reads it** — inside the one function or method that reads it, or on the one class; module scope is for values two or more share. Exceptions: tunables are keyword arguments (above), and the `*_ENTRY` subprocess entry-point strings stay at module scope because [tests/test_subprocess_entry_points.py](tests/test_subprocess_entry_points.py) finds them by AST-scanning module-level assignments — inlining one silently drops it from that guard.
- **Classmethods vs free functions in `api/`.** Alt-constructors use `@classmethod`: `Cls.from_X(x, ...)` for data-taking factories (`Interval.from_bounds`), `Cls.create_X()` for parameterless well-known instances (`DiffractionMetadata.create_null`); domain-verb names (`PluginRegistry.load_plugins`) mark a side effect `from_*` doesn't convey. Avoid `@staticmethod` — helpers touching neither `self` nor `cls` go to module scope, `_`-prefixed when private. Per-object analyzers returning a small dataclass are free `compute_*`/`estimate_*` functions in the activity-verb module ([metrics.py](src/ptychodus/api/metrics.py), [preprocess/](src/ptychodus/api/preprocess/)), even when the dataclass lives elsewhere.
- **No nested function definitions.** A helper is a module-level function, `_`-prefixed when private, or a method of a class that owns the state it shares; its inputs are parameters, not variables captured from an enclosing scope. A closure hides what it depends on, cannot be tested or reused, and grows into a second function body inside the first. Decide where each piece belongs instead: inline it (one use, a few lines), lift it to a private module-level function, give shared state to a small class with methods — a `scipy.sparse.linalg.LinearOperator` subclass, as `VSPILinearOperator` is, not a `matvec` closure — or, when it is useful beyond its caller, make it public in the module that owns the concept, as `api/patch.py` owns batched patch placement. Bind arguments with `functools.partial` where an API takes a callable. Exempt are functions a framework registers by decorator inside a factory (MCP tools, FastAPI routes and lifespans, SQLAlchemy event listeners), callbacks whose signature a library fixes and which need state a `partial` cannot carry (signal handlers, executor work items), and tests. A one-expression `lambda` is fine.
- The `webapp/ui/` frontend is TypeScript compiled to native ES modules by plain `tsc` — no bundler, framework or runtime npm deps. The gitignored `ui/dist/` ships in the sdist and wheel via `[tool.setuptools.package-data]`, so a PyPI install never needs Node. [setup.py](setup.py) compiles it from **both** the `sdist` and `build_py` cmdclasses — `build_py` alone leaves the tarball without a UI. A missing `tsc` warns and builds without the UI; `PTYCHODUS_WEBAPP_REQUIRE_UI_BUILD=1` (release builds) makes it fatal.
- **`cli/` versus `scripts/`.** `src/ptychodus/cli/` holds the `[project.scripts]` modules and shared argparse/logging helpers, and ships in the wheel; a new console command goes there with an entry point. The services are the exception: `ptychodus-webapp` and `ptychodus-agent` each keep `cli.py` in their own package, which ships only with its extra. A command module may import, at module scope, the extra its own command needs, and so may a private helper shared only by commands needing that same extra. `cli/__init__.py` holds what every command shares, `CancellationToken` and `install_signal_handlers` among it. `_reconstruct_common.py` is shared by every reconstruct command and imports no reconstruction library, so `ptychodus-reconstruct` and `ptychodus-reconstruct-subprocess` load without pty-chi; it reaches pty-chi only inside the functions the pty-chi drivers call. `cli/__init__.py` and every command that works on a bare install stay free of optional extras, and [tests/test_cli_entry_points.py](tests/test_cli_entry_points.py) skips a command whose extra is absent. The top-level `scripts/` is **not** packaged — checkout-run one-off and facility tooling. The `ptychodus-reconstruct-<beamline>` drivers are short `InstrumentProfile`s over `_reconstruct_standard.py`, all but `reconstruct_pear.py` (JSON parameters) and `reconstruct_batch_lamni.py` (YAML settings, multi-GPU). A plugin name a driver passes resolves only at run time, so [tests/test_cli_plugin_names.py](tests/test_cli_plugin_names.py) reads every one from the source and checks it against the registry — rename a plugin and its drivers in the same commit, and map a new name-bearing field in its `_CATALOGS`. `--prepare-only` writes a prepared directory (`diffraction.h5`, `product.h5`, `reconstruct_options.yaml`) for `ptychodus-reconstruct` (`reconstruct_prepared.py`), which reconstructs it with whichever library the options document names. `reconstruct_subprocess.py` is a pipe-driven child for a launching process.
- **PyTorch comes from a pinned index, chosen by extra.** `ptychi` installs a CPU torch and each `ptychi-cuda*` extra the matching CUDA build, mirroring the CUDA versions `scripts/podman/build` targets; `[tool.uv.sources]` in [pyproject.toml](pyproject.toml) pins them and `[tool.uv] conflicts` keeps them exclusive. Only uv honors this — `pip install ptychodus[ptychi]` takes PyPI's default CUDA torch, which is why [containers/](containers/) install their own first. A build newer than the driver's CUDA ceiling silently runs on the CPU; `ptychodus-system-check --require-cuda` gates that.
- **All documentation is Markdown.** `docs/source/*.md` is MyST, parsed by `myst_parser`; no reStructuredText remains and no new `.rst` should be added. Sphinx constructs use MyST directive fences — ` ```{note} `, ` ```{toctree} ` — with `:option: value` lines directly under the opening fence and a blank line before directive content. Autodoc stanzas stay raw reStructuredText inside ` ```{eval-rst} ` blocks. Roles use MyST syntax: `` {py:class}`…` ``, `` {ref}`…` ``. Enabled MyST extensions are declared in [docs/source/conf.py](docs/source/conf.py).
- **Markdown style** — `uv run pymarkdown scan $(git ls-files '*.md')` and the `pre-release` skill's house-style scan enforce all but the judgment calls: ATX headings, one H1 per file, `###` max outside `docs/source/` (MyST may use `####`); backtick fences tagged `sh`, not `bash`; `-` bullets, ordered lists numbered for real; inline links relative to the linking file, bare URLs as `<https://…>`; pipe tables with outer pipes and an unpadded `| --- |` separator; **no hard wrapping**; `**bold**` for identifiers, paths and warnings, backticks for code, em dash `—` for asides; YAML front matter only in `.claude/skills/*/SKILL.md`. Nested content indents to the parent's content column — 3 spaces under an ordered marker, 2 under a dash.

### Terminology

Names follow standard x-ray ptychography usage, one term per concept, in identifiers, UI text, help text, docstrings and prose alike. Code and the webapp rename freely to these terms (identifiers, REST and MCP names, JSON fields, CLI flags), with no aliases; a data format — HDF5 and CXI keys, manifest keys, file names, INI settings keys, user-written YAML keys — changes only by an explicit decision, and the ones kept are listed last.

- **Probe positions** are where the probe illuminates the object (identifiers `probe_position(s)`), not "scan positions", "scan points", "scan path" or "trajectory". The **probe path** is the probe positions joined in order; a **scan pattern** is the geometry a generator lays out (spiral, Lissajous).
- A **scan** is one acquisition, as in scan number — never a set of positions.
- **Diffraction patterns** are the measured intensities, one per probe position (identifiers `pattern(s)`). A **frame** is a raw detector readout before assembly, or a coordinate frame (the exit frame); statistics over patterns are the mean, minimum and maximum **pattern**.
- The **scan index** pairs a pattern with a position; **pattern indexes** and **position indexes** are each side's. The plural is **indexes**; **indices** is for numpy subscripts only.
- The **probe** is the complex illumination function. **Illumination** is only the probe intensity summed over positions (the illumination map); **beam** is the incident x-ray beam and its centre on the detector.
- The **object** is the reconstructed transmission function; the **sample** is the physical specimen it describes (sample name). Not "specimen".
- A **product** is a probe, an object and probe positions with their metadata, whether guessed or reconstructed. **Reconstruction** is the process, and loosely a product a reconstructor produced; "result" and "output" do not name a product.
- An **initial guess** is the probe, object or probe positions a reconstruction begins from; a **warm start** takes it from an earlier product or file, a **cold start** generates it. A **generator** (`ObjectGenerator`, `ProbeGenerator`, `ProbePositionsGenerator`) **generates** one, and the GUI's object, probe or probe-position **source** is a generator or a file — always qualified, since bare "source" collides with the X-ray source. Not "starting guess", "initialization" (except in a library's own API), "object/probe model", or "builder" in user-facing text; the model layer's `*Builder` classes are internal. "Start" is kept only for what the spectral refinement iterates from.
- **I0** is the per-position incident-flux reading (ion chamber, diode, scaler), **calibrated** when converted to photons; the **detector sum** is a pattern's summed counts. Not "monitor", "measured" (for I0), "totals" or "total counts". The **probe photon count** is photons per exposure only.
- A **reconstruction library** (or just **library**) is a package that reconstructs — pty-chi, cdtools, PtychoPINN — exposed as a `*ReconstructorLibrary`; an **algorithm** is a method within it (LSQML, ePIE); a **reconstructor** is the object implementing one algorithm, a **trainable reconstructor** one that also trains. Not "backend", "engine" or "trainer".
- **Options** are a pydantic declaration and its options document; **parameters** are live `Parameter[T]` values in `model/`; **settings** are the INI registry and its files; **configuration** is a command's own YAML (the stream's).
- An **action** is reconstruct, train or enhance; a **run** is one execution of an action, recorded by `RunRecord`, and its **run resource** is the product or fluorescence resource whose manifest carries that record. A **command** is a `ptychodus-*` entry point, a **job** a unit in a remote scheduler, a **task** GUI background work, a **process** an operating-system process. A **turn** is one prompt to the integrated agent and its answer, never a run; AG-UI's own names (`RunAgentInput`, `RUN_STARTED`) stay as the protocol spells them.
- **Progress** counts epochs for a reconstruction or training and elements for an enhancement; a **checkpoint** is the immutable result at one progress value, not a "snapshot".
- **Model** is always qualified: the **trained model**, the **forward model**, the **model layer**, the **language model**.
- A **device** is anything a computation runs on, the CPU included — not "accelerator".
- **Fluorescence** names identifiers; **XRF** appears only where a name already carries it (`ptychodus-enhance-xrf`, the XRF-Maps format). An **element map** is one element's channel; an **enhancer** turns a **measured** dataset into an **enhanced** one — not "enhancement strategy".
- The **webapp** is the `ptychodus-webapp` service, and its **web UI** the browser front end. The **storage root** is the on-disk tree; a **resource** is one folder in it with its manifest and data, and its **kind** is campaign, diffraction, product or fluorescence; the webapp keeps a **metadata cache** of them. Not "store", "artifact" or "catalog". **Dataset** names only `DiffractionDataset` and `FluorescenceDataset`.
- The **GUI** is the PyQt application — not "desktop app".
- **Kept data-format names**, which the terms above do not override: HDF5 and CXI keys (`probe_photon_counts` holds per-position I0); the INI keys `TotalCounts*`, `NumberOfPointsToDiscard*` and each section's `Builder`; stream and batch YAML keys and values such as `total_counts_lower_bound`, `object_generator` and `probe_source: simulated`; an enhancer's options-document selector `algorithm`; and option names a library declares (pty-chi's `num_sync_epochs`, PtychoPINN's `accelerator`).

**Never commit without being asked.** Finish the work, run the gate, and leave the changes in the working tree — staged if asked, unstaged otherwise.
