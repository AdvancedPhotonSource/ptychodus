# CLAUDE.md

## Project

Ptychodus is a ptychography data-analysis application that ingests instrument data, prepares it for processing, and dispatches it through pluggable reconstruction libraries (PtyChi, PtychoPINN, and others). It runs as a PyQt5 GUI, a headless batch CLI, and a streaming processor inside beamline pipelines (pvapy area-detector). Python ≥3.11, `uv` preferred.

## Common Commands

```sh
uv sync --extra globus --extra gui --extra ptychi   # dev install; ptychi is CPU torch
uv sync --extra globus --extra gui --extra ptychi-cuda128  # GPU: match nvidia-smi's CUDA ceiling
uv run ptychodus                                    # GUI
uv run ptychodus -b reconstruct -i <in> -o <out>    # batch — reads StandardFileLayout in <in>/
uv run pytest                                       # tests
uv run ruff check . && uv run ruff format --check . # lint + format
uv run mypy src/ptychodus src/ptychodus_store scripts tests  # types (wider than CI's)
```

Container builds: `scripts/podman/build` (Dockerfiles live in [containers/](containers/); tags are `ptychodus:<version>-<variant>` over the `DEFAULT_VARIANTS` the script declares — a CPU build, one per supported CUDA, ROCm and XPU); launcher `scripts/podman/ptychodus` auto-detects the GPU family and, on NVIDIA, the newest built CUDA variant the host driver supports. Docs: `make -C docs html`.

Other entry points (`convert-to-ptychodus`, `ptychodus-store` and the rest) are listed in [pyproject.toml](pyproject.toml) `[project.scripts]`; their modules live in [src/ptychodus/cli/](src/ptychodus/cli/). Unpackaged operator tooling — the podman wrapper and the per-facility HPC token/submit helpers — lives in the top-level [scripts/](scripts/) and is run from a checkout, e.g. `python scripts/genesis/ptychodus_iri_tokens.py`. The store service has its own docs: [src/ptychodus_store/README.md](src/ptychodus_store/README.md).

### Testing

Tests cover `api/`, `model/`, `view/widgets/` and `controller/rendering/`, plus the two modules under `controller/` that carry real logic rather than plain Qt wiring: [controller/parameters.py](src/ptychodus/controller/parameters.py) (unit conversion, unit selection, and signedness inference in its view controllers) and [controller/processing/generated.py](src/ptychodus/controller/processing/generated.py), whose gate nesting, plan folding and widget-kind rules decide every backend’s panel layout from what that backend declares — most of it a pure `Sequence[DescribedField] -> list[_Item]` pipeline that needs no widget to exercise. A reusable widget carrying logic of its own belongs in `view/widgets/`, where it is covered without an exception; that is where `DecimalRangeSlider` lives. `controller/rendering/` is covered the same way rather than as an exception: it imports no Qt, so its tests live at `tests/` root and run on a bare install like any `api/` or `model/` test. **Do not add tests for anything else under `view/` or `controller/`**, including controller helper functions. Qt tests depend on PyQt5, which is an optional extra (`--extra gui`); the whole `tests/view/` and `tests/controller/` subtrees are dropped in [tests/conftest.py](tests/conftest.py) via `collect_ignore` when `find_spec('PyQt5')` returns `None`, mirroring the `ptychodus_store` gate. That conftest also hosts the shared session-scoped `qapp` fixture, which imports `QApplication` inside the fixture body so the conftest itself stays importable on a bare install. `pytest tests/` must pass on a bare `pip install .` (that is what CI runs), so anything reachable from `ptychodus.model` at import time must be free of optional dependencies: a reconstructor backend names its modules in `requires=` and imports them inside `_build()`; any other optional subsystem keeps its dependency behind a deferred import the same way. Guard a test that needs an optional backend with `pytest.importorskip('ptychi')`; drop a whole optional-extra directory with `collect_ignore` in [tests/conftest.py](tests/conftest.py) — `importorskip` in a conftest is reported as an error, not a skip.

## Architecture

### Three-layer separation: api / model / view+controller

- **`src/ptychodus/api/`** — pure-Python domain layer with **no** GUI or model dependencies. Core data structures (`Product`, `ProbeEnsemble`, `Object`, `ProbePositionSequence`, `DiffractionDataset`, `AssembledDiffractionData`), abstract interfaces (`DiffractionFileReader/Writer`, `ProductFileReader/Writer`, `Reconstructor`, `TrainableReconstructor`, `WorkflowAPI`), and infrastructure (`Observable`/`Observer`, `Parameter`/`ParameterGroup`, `SettingsRegistry`, `PluginRegistry`/`PluginChooser`). Module naming follows SciPy conventions: activity-verb form for verb-based operations (`interpolate`, `visualize`, `reconstruct`, `propagate`, `simulate/`, `preprocess/`); plural-collection form for infrastructure (`plugins`, `settings`, `parameters`, `constants`, `typing`); singular nouns for domain data types (`affine` owns `AffineTransform`, its decomposition, the estimator that fits one, and the product-level correction that applies it). `simulate/` hosts forward models (`simulate/diffraction`, `simulate/object`, `simulate/probe`, `simulate/probe_positions`); `preprocess/` hosts preprocessing pipelines (`preprocess/diffraction`, `preprocess/noise`). This layer depends on nothing else in ptychodus.
- **`src/ptychodus/model/`** — application logic. Most subpackages (`diffraction/`, `product/`, `processing/`, `fluorescence/`, `analysis/`, `globus/`, `genesis/`, and others) expose a `*Core` class owning their settings, repositories, and APIs. Reconstructor backends expose a `*ReconstructorLibrary` instead and live under `plugins/`, where they are discovered rather than composed. `model/core.py::ModelCore` is the composition root that constructs them all in dependency order. Used by the GUI *and* by `__main__.py` batch mode.
- **`src/ptychodus/view/`** (PyQt5 widgets, no logic) and **`src/ptychodus/controller/`** (mediates widgets↔model). Mirror the model layout. `view/core.py::ViewCore` and `controller/core.py::ControllerCore` are composition roots; the navigation toolbar order in `ViewCore` is the source of truth for left/right stacked-panel indexes. `controller/rendering/` is the one part of the layer that is not mediation: Qt-free array-to-color transformation (`VisualizationEngine` and its renderers), which only the GUI drives, so `ControllerCore` builds every engine and no `*Core` holds one. Two `__init__.py` files are deliberately empty and say so — `controller/` so that `controller/rendering/` stays importable without PyQt5, and `controller/diffraction/` to break an import cycle with `controller/product/`; import both composition roots from their `core` modules.

The GUI is optional: `__main__.py` falls back to headless if PyQt5 is missing. `ptychodus_stream_processor.py` (the `PtychodusAdImageProcessor`) is a third entry mode, imported only when `pvapy` is available.

### Index-based pattern/position association

Diffraction patterns and probe positions are paired by **integer scan index**, never by array order. This is what makes streaming and mismatched-rate ingest robust.

- Producers: `DiffractionArray.get_indexes()` (`api/diffraction.py`); `ProbePosition.index` (`api/probe_positions.py`).
- Matcher: `prepare_reconstruct_input(assembled_data, product, ...)` in `api/reconstruct.py` treats pattern indexes as authoritative — duplicate position indexes are averaged into anchors, pattern indexes inside the anchor range without an exact position are linearly interpolated, and pattern indexes outside the anchor range are dropped (no extrapolation).
- Round-trip: HDF5 and NPZ product writers persist position indexes via `ProductFileKeys.PROBE_POSITION_INDEXES`.
- Line-major indexes: an instrument whose positioner is driven over more points per scan line than its detector records cannot use a running count on either side — the pairing slides by the surplus, one line at a time, while every pattern still finds a match. Both readers instead number a point `line * RASTER_LINE_INDEX_STRIDE + column` (`plugins/mda/mda_position_file.py`), opted into per registration by the `line_index_stride` keyword on `MDAPositionFileReader` and `APS2IDDiffractionFileReader`. Surplus commanded points then go unclaimed, a short line claims fewer, and a detector line past the end of the positioner record is dropped — all by the matcher above, unchanged. Only registrations that pass the keyword opt in; the default numbering is untouched.

### Plugin system

`api/plugins.py::PluginRegistry.load_plugins()` walks `ptychodus.plugins.*` with `pkgutil.iter_modules` and calls each module's `register_plugins(registry)`. Module-load failures are logged and skipped — this is how optional-dependency plugins (LCLS, NSLS-II, …) silently disable themselves. Never make plugin loading fatal.

### Settings & observers

Settings flow through `api/parameters.py::Parameter[T]` and `ParameterGroup`. Each `*Core` calls `settings_registry.create_group(name)` and creates typed parameters. `SettingsRegistry` serializes the tree as INI. React to settings changes via `Observer`/`Observable` (`api/observer.py`); `model/parameters.py::PluginChooserParameter` adapts a `PluginChooser` into a settings-backed `Parameter[str]` and is the typical bridge for "settings string → selected plugin" — the reconstructor selection is two of these in series, a library chosen from the chooser and an algorithm resolved against whichever library that is. Hook observers rather than poll.

**Two idioms, and which is current.** The hand-written `*Settings` class above backs every subsystem and is what a new `*Core` writes. The reconstructor backends use a second one: a backend returns a nested pydantic object from `Reconstructor.get_default_options()` stating what it accepts, and `model/processing/` generates the live parameters, the flat INI keys, the display text and the Qt panel from that declaration — `flatten.py` projects it, `generate.py` builds the parameters, `parameter_store.py` holds them, and a per-backend table says where each option is persisted. The generated path is reached only through `ProcessingParameterStore`, so it is not available to a non-reconstructor subsystem; the flattener and the tables are explicitly transitional and retire with the Qt panels. What both idioms owe: a parameter states its bounds where it is declared, because `controller/parameters.py` raises on a missing one rather than degrading, and infers signedness from the minimum.

### Standard HDF5 layout (external interface — change carefully)

`api/io.py::StandardFileLayout` is the canonical contract for batch mode, remote workflows and the `ptychodus-reconstruct-*` drivers: `diffraction.h5`, `product.h5`, `fluorescence.h5`, `ptychi_options.yaml`, `settings.ini`, `ptychodus.log`, plus a `model` stem whose extension the trainable backend supplies. The input/output distinction lives in the containing directory (batch mode takes `-i` and `-o`; remote-workflow backends stage under `<workflow_root>/input/` and `<workflow_root>/output/`). The enum also exposes `path(directory)` and `checkpoint_path(directory, epoch)` helpers — the latter builds `<stem>.<epoch:06d><suffix>`, the per-epoch snapshot convention for streaming reconstructions. Key names live in `DiffractionFileKeys` / `ProductFileKeys` enums — external consumers depend on them. CXI paths ptychodus writes live in `CXIFileKeys`, and `CXIVariant` chooses the layout a CXI writer produces; readers detect the layout and take no variant.

### Reconstructor libraries

Each backend exposes a `*ReconstructorLibrary`, and the base in [api/reconstruct.py](src/ptychodus/api/reconstruct.py) owns everything except what the backend actually builds. A subclass passes `requires=` — the modules it cannot work without — and implements `_build()`; the base resolves those names without importing them (`is_available()`), calls `_build()` once on first `__iter__`, and announces whatever happens through the library's own logger: the version on success, `<distribution> not found.` at INFO when the modules are absent, and a distinct **warning** carrying the traceback when they resolve but `_build()` raises `ImportError` — a fault rather than a choice, and the one case that must not read as an uninstalled backend. So a backend writes no availability logic, never imports its dependency at module scope, and costs nothing in a process that registers plugins but never reconstructs. The base also tells each reconstructor it built where its child code lives — `_subprocess.py` in the library's own package — so a backend writes no entry-point string and every child is spawned through one dispatcher. A library does not name itself: it is named where it registers, and that name is what the section table and the parameter store are keyed on. The surface stays stable whether or not the backend is installed, so `ModelCore` hands `ProcessingCore` the whole chooser and `ProcessingCore` answers which backends are in play. Reconstructors yield `ReconstructOutput` per iteration so the GUI can stream progress.

### Remote compute

Both providers are optional-dep gated but constructed by `ModelCore` even when disabled:

- `model/globus/` — Globus Compute (original APS workflow).
- `model/genesis/` — IRI/AmSC HPC via `facility_adapters.py`, with per-facility scripts under `scripts/genesis/{alcf,nersc,olcf}/`.

`WorkflowAPI` (`api/workflow.py`, `model/workflow.py::ConcreteWorkflowAPI`) is the unified façade GUI, batch, and remote drive.

### ptychodus_store service

`src/ptychodus_store/` is a **separate package** adjacent to `ptychodus`, not a subpackage. It reads-only from `ptychodus.api` and **must not import `ptychodus.model` or `ptychodus.view`**. Surface: FastAPI REST under `/api/v1/*`, MCP server at `/mcp`, minimal TypeScript UI at `/ui/`, SQLite metadata cache reconciled by a watchdog observer. Composition root: `create_app()` in `app.py`. Deployment details in [src/ptychodus_store/README.md](src/ptychodus_store/README.md).

## Conventions

- Ruff: **single-quoted** strings, 100-char lines, py311 target. Enabled rules: F, N, NPY.
- Preserve unit suffixes on physical quantities (`probe_energy_eV`, `set_value_from_string`) — silence naming lints with `# noqa: N802/N806/N815`, don't rename.
- Type hints are mandatory. `pyproject.toml` lists modules whose missing stubs are intentionally ignored — keep new code typed and don't widen that list.
- `ModelCore.is_developer_mode_enabled` is `True` when the effective log level ≤ DEBUG (`--log-level 10`); some controllers gate features (Agent panel, probe-position analysis) behind it.
- HTTP-client code uses `httpx` throughout (sync `httpx.Client` for repeated calls, module-level `httpx.get/post` for one-shots). `requests` is not a dependency.
- Prefer affirmative conditionals when both branches do meaningful work — `if x.is_file(): ... else: ...`, not the negated form. Guard clauses that early-return are still idiomatic.
- **No forward references in comments.** A comment or docstring explains what the code guarantees, not who consumes it. Naming a caller is wrong the moment one is added, moved or renamed. In `api/` it is worse than stale: naming a `model/` or `cli/` symbol inverts the layering the package exists to enforce, even in prose. Describing what the code itself depends on is fine — an import already states it.
- **numpy → Python scalar in `api/`.** Cast only at the boundary — the `return` of a function annotated `-> float`/`-> int`/`-> bool`, or assignment to a Python-typed dataclass field. Everywhere else let numpy scalars propagate through arithmetic. When you do cast, use the constructor (`float(...)`, `int(...)`, `bool(...)`, `complex(...)`), never `.item()` — mypy sees the target type, and it matches the HDF5-read pattern in [io.py](src/ptychodus/api/io.py).
- **Underscore-prefixed names in `api/`.** A name is public iff production code outside `api/` uses it **or** the module's `__all__` lists it; everything else, including helpers shared across modules within `api/`, is `_`-prefixed, and renames on promotion. Tests are exempt — pinning an invariant does not promote a helper. Rather than import another module's underscore name, move the logic onto a peer method of the shared abstract base, as `BinningStep.apply_to_dtype` does. Audit with `rg -Un --pcre2 'from ptychodus\.api\.[\w.]+ import (\([^)]*\b_|_)' src/ scripts/` — `-U` catches the parenthesized import form, `[\w.]+` the dotted submodules.
- **Pipeline steps declare their dtype effect.** Any `DiffractionPrepStep` whose `apply()` widens value range (summing, scaling, accumulating) must override `apply_to_dtype(dtype)` to return a dtype holding the promoted result, and its `apply()` must produce that dtype — typically `numpy.sum(..., dtype=self.apply_to_dtype(data.dtype))`. Sister method of `apply_to_extent` and `apply_to_pixel_geometry`; the default is identity. Callers allocating a pre-sized buffer fold it via `compute_assembled_dtype` (the pipeline's `compute_output_dtype`, then `DetectorCorrections.apply_to_dtype` for a background or flat field applied after it), so the buffer is wide enough by construction rather than by `isinstance` checks in the allocator. An additive per-pixel map follows the pipeline through `apply_to_pixel_map`, which a step overrides where a map must not take the pattern path (a dtype cannot tell a float map from a float pattern).
- **Tunables are keyword arguments, not module constants.** A numeric threshold, tolerance, epsilon or floor that changes what a function returns is keyword-only with a default (`def compute_probe_overlap(product, *, roundoff_floor: float = 1.0e-12)`), its effect documented in the docstring. The test is whether a caller could plausibly want a different value; if yes it belongs in the signature, with the default on the public entry point so private helpers do not duplicate the literal. Private module constants stay only for values callers must not vary: data tables (`_FLUORESCENCE_LOAD_PATHS`), precompiled objects (`_UNSAFE_PATH_CHARS`), mathematical invariants (`_AFFINE_MINIMUM_POINTS`).
- **A private constant lives in the narrowest scope that reads it.** A module-level `_CONSTANT` read by exactly one function or method belongs inside it, and one read only by a single class belongs on that class: the name is then in view of the only code it governs, and a reader need not scan the module to confirm nothing else depends on it. Module scope is for values two or more of them share. Two exceptions, both because something other than the reader needs the name: a value a caller could plausibly want to vary is a keyword argument instead (see the tunables rule above), and the `*_ENTRY` subprocess entry-point strings must stay at module scope because [tests/test_subprocess_entry_points.py](tests/test_subprocess_entry_points.py) discovers them by AST-scanning module-level assignments — inlining one drops it from that guard with nothing to show for it.

- **Classmethods vs free functions in `api/`.** Alt-constructors on domain types use `@classmethod`, split by naming: `Cls.from_X(x, ...)` for data-taking factories (`Interval.from_bounds`) and `Cls.create_X()` for parameterless factories of well-known instances (`DiffractionMetadata.create_null`). Domain-verb names (`PluginRegistry.load_plugins`) are reserved for factories with a side effect `from_*` doesn't convey. Avoid `@staticmethod`: helpers touching neither `self` nor `cls` go to module scope, `_`-prefixed when private. Per-domain-object analyzers returning a small dataclass live as free `compute_*` / `estimate_*` functions in the activity-verb module — [metrics.py](src/ptychodus/api/metrics.py), [preprocess/](src/ptychodus/api/preprocess/) — even when the result dataclass is defined elsewhere.
- The `ptychodus_store/ui/` frontend is TypeScript compiled to native ES modules with plain `tsc` — no bundler, no framework, no runtime npm deps. The compiled `ui/dist/` is gitignored but ships in both the sdist and the wheel via `[tool.setuptools.package-data]`, so installing from PyPI never needs Node. [setup.py](setup.py) compiles it from **both** the `sdist` and `build_py` cmdclasses — hooking only `build_py` leaves the tarball without a UI. A missing `tsc` warns and builds without the UI; `PTYCHODUS_STORE_REQUIRE_UI_BUILD=1` (set by release builds) makes that fatal.
- **`cli/` versus `scripts/`.** `src/ptychodus/cli/` holds the modules behind `[project.scripts]`: it ships in the wheel, carries the shared argparse and logging helpers, and must stay free of optional-extra imports so the bare-install commands keep working. The top-level `scripts/` is **not** packaged — checkout-run operator tooling invoked as `python scripts/…`. A new console command goes in `cli/` with an entry point; a one-off or facility script goes in `scripts/` with none. The per-beamline `ptychodus-reconstruct-<beamline>` drivers live in `cli/` for the same reason; all but `reconstruct_pear.py` (JSON parameter file) and `reconstruct_batch_lamni.py` (YAML settings file, fanning scans across the visible GPUs) are a short `InstrumentProfile` over `_reconstruct_standard.py`, so a new beamline is a profile rather than a copy. (`reconstruct_subprocess.py` is a pipe-driven child, unrelated to the in-process `multiprocessing` child in `plugins/ptychi/_subprocess.py`.)
- **PyTorch comes from a pinned index, chosen by extra.** `ptychi` installs a CPU torch; each `ptychi-cuda*` extra installs the matching CUDA build, mirroring the CUDA versions `scripts/podman/build` builds images for. `[tool.uv.sources]` in [pyproject.toml](pyproject.toml) does the pinning and `[tool.uv] conflicts` keeps the extras mutually exclusive. Two consequences: only uv honors this, so `pip install ptychodus[ptychi]` still takes PyPI's default CUDA torch (which is why [containers/](containers/) arrange their own torch first); and a build newer than the host driver's CUDA ceiling leaves `torch.cuda.is_available()` false, so reconstruction silently runs on the CPU. `ptychodus-system-check --require-cuda` gates that.
- **All documentation is Markdown.** `docs/source/*.md` is MyST, parsed by `myst_parser`; no reStructuredText remains and no new `.rst` should be added. Sphinx constructs use MyST directive fences — ` ```{note} `, ` ```{toctree} ` — with `:option: value` lines directly under the opening fence and a blank line before directive content. Autodoc stanzas stay raw reStructuredText inside ` ```{eval-rst} ` blocks. Roles use MyST syntax: `` {py:class}`…` ``, `` {ref}`…` ``. Enabled MyST extensions are declared in [docs/source/conf.py](docs/source/conf.py).
- **Markdown style**, partly enforced by `pymarkdownlnt` (`uv run pymarkdown scan $(git ls-files '*.md')`), the rest house convention: ATX headings, one H1 per file, `###` max outside `docs/source/` (MyST pages may use `####`); backtick fences never tildes, shell tag `sh` not `bash`; `-` bullets, ordered lists with real incrementing numbers; inline links with repo-relative paths, bare URLs as `<https://…>` autolinks; pipe tables with leading and trailing pipes and an unpadded `| --- |` separator; **no hard wrapping**, one physical line per paragraph; `**bold**` for identifiers, paths and warnings, backticks for code tokens, em dash `—` for asides; no YAML front matter except `.claude/skills/*/SKILL.md`. Fences and sub-lists nested in a list item indent to the parent's content column — 3 spaces under an ordered marker, 2 under a dash.

## Repository

CI targets `main`; local dev branches (e.g. `amsc`, `webservice`) are active — confirm the intended target before opening PRs.

**Never commit without being asked.** Finish the work, run the gate, and leave the changes in the working tree — staged if asked, unstaged otherwise. This holds even when a commit seems obviously wanted: an approved plan that describes commits is a plan for the code, not permission to write history; a clean gate is not permission either; and neither is a long task with natural checkpoints. Say what is ready and let the commit be a separate instruction. The same goes, more so, for `git push`, `git commit --amend`, `git reset`, force-pushing, and opening or updating PRs.
